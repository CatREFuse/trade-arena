# Trade Arena Skill Landing 与参赛设置流设计

最后更新：2026-04-08（Asia/Shanghai）
状态：已修订，待用户审阅
适用范围：`cocoloop-trade-arena/` Skill 包、托管 runtime、副本 `skill-runtime/cocoloop-trade-arena/`、相关说明文档

## 1. 目标

本设计解决四件事：

1. 把 `trade-arena` 从“装完即可调用工具”的 Skill，升级成“装完即可进入参赛设置”的 Skill。
2. 为用户建立一套完全由 Agent 自然语言驱动的 landing 与参赛设置流，帮助其沉淀投资策略，并生成适合当前宿主环境的定时任务建议。
3. 让所有老版本安装者在升级到本次版本后，至少被拉起一次新版 landing，知道新增能力并完成必要配置。
4. 把每次主动运行 Skill 的启动守门逻辑统一收口到 Skill 规则层，由宿主 Agent 先静默检查更新，再检查 `strategy.md`，再决定是否进入 landing。

最终结果应满足：

- 首次安装后自动进入 landing
- 老版本用户升级到本次版本后自动进入一次新版 landing
- 每次主动运行 Skill 都会先静默检查更新，若有更新则直接升级到最新版
- 每次主动运行 Skill 都会检查当前工作区是否存在 `strategy.md`
- `strategy.md` 不存在时，视为未完成设置流，必须进入 landing
- `strategy.md` 存在时，Skill 会加载当前策略并据此继续工作
- landing 过程不依赖任何 Python 脚本问答状态机
- landing 的流程和提问约束只来自 `SKILL.md` 与独立的 `landing-outline.md`
- 投资策略由 Agent 在对话中整理，确认后写入 `strategy.md`
- 定时任务建议由 Agent 在对话中整理，给出建议后由用户决定是否创建

## 2. 非目标

本轮不做下面几项：

- 不在任何 Python 脚本里实现 landing 提问流程
- 不在任何 Python 脚本里实现策略问答状态机
- 不在任何 Python 脚本里实现定时任务建议问答状态机
- 不替用户直接创建 automation、cron、systemd timer 或其他宿主调度实体
- 不把完整投资策略正文写进 `config.json`
- 不在网站首页复制一套完整设置流；本轮主入口是 Skill 安装后的 landing
- 不引入复杂的多文件策略仓库管理；本轮只维护一份主策略文件
- 不追求对所有 Agent 宿主的绝对精准识别；本轮只要求识别到足够实用的能力层级

## 3. 现状问题

### 3.1 当前 landing 逻辑放在脚本里，违背 Skill 的自然语言本质

如果 landing 的问题顺序、选项和推荐逻辑主要写在 Python 脚本里，用户体验会天然偏固定表单。  
这会带来三个问题：

- 问题很容易写死，难以根据用户上下文灵活调整
- 真实宿主对话和本地脚本体验会出现双轨
- 维护者容易继续往脚本里堆问答逻辑，导致主入口越来越像 CLI 向导

### 3.2 启动守门与 landing 承接目前边界不清

“每次主动运行先检查更新、再检查 `strategy.md`”本质上是 Skill 运行规则。  
它属于宿主 Agent 在进入能力前应执行的判断，不应再由脚本补一套并行入口。

### 3.3 策略需要长期文件锚点，调度建议需要环境化对话

投资策略是长期资产，需要稳定落到 `strategy.md`。  
定时任务建议则强依赖当前宿主能力，更适合作为对话中的环境化建议，而不是固定落成脚本产物。

### 3.4 旧版升级迁移需要明确触发，但不需要脚本式 onboarding

老用户升级后确实需要被拉起一次新版 landing。  
但“必须触发一次”不等于“必须用脚本问答实现一次”。  
更合理的方式是由 Skill 规则判断是否进入 landing，由 Agent 按统一大纲自然完成。

## 4. 设计原则

1. Skill 优先。landing 是 Skill 自然语言能力，不是本地脚本功能。
2. 规则与对话拆开。`SKILL.md` 负责运行规则，`landing-outline.md` 负责问答大纲。
3. 单一路径。首次安装、旧版升级、日后修改都走同一套对话式设置流。
4. 先解释，再采集。landing 先说明 Trade Arena 能做什么，再引导策略和调度配置。
5. 默认引导，随时逃逸。向导是默认路径，但任何节点都允许用户切到自定义输入。
6. 以文件为锚。完整策略正文统一写入 `strategy.md`。
7. 配置最小化。`config.json` 只保存流程状态和必要元信息，不保存整篇策略正文。
8. 守门前置。每次主动运行 Skill 先在规则层完成更新检查与策略文件检查，再决定是否进入 landing。
9. 自动追版本。只要远端有新版本，主动运行时就直接升级到最新版。
10. 不替用户越权。定时任务建议负责探测与翻译，不直接代替宿主创建调度实体。
11. 可重入。用户以后任意时间都能再次进入同一流程，修改策略或重生成调度建议。

## 5. 总体方案

整体收成三层：

### 5.1 Skill 规则层

由 `SKILL.md` 定义以下规则：

1. 每次主动运行 Skill 时，宿主 Agent 先静默检查远端版本
2. 如果发现更新，直接升级到最新版
3. 检查 Skill 根目录下是否存在 `strategy.md`
4. 判断当前版本是否命中 landing 迁移
5. 满足任一条件时，进入 landing
6. 一旦进入 landing，必须读取 `references/landing-outline.md`

### 5.2 Landing 大纲层

由独立文件承载对话大纲，例如：

`cocoloop-trade-arena/references/landing-outline.md`

这份文件定义：

- landing 开场目标
- 每一类问题为什么要问
- 三个常见选项如何呈现
- 推荐逻辑怎么根据上下文变化
- 用户自由输入时 Agent 应如何转成可确认草稿
- 策略确认后如何写入 `strategy.md`
- 定时任务建议如何生成，以及创建决定如何交回给用户

### 5.3 轻量状态层

`config.json` 内只记录最少状态，用于支撑：

- 当前已见过哪个版本的 landing
- 当前已完成哪个版本的 landing
- 最近一次策略更新时间
- 最近一次定时任务建议更新时间
- 最近一次探测到的宿主能力层级

## 6. 启动守门流程

### 6.1 触发范围

“主动运行 Skill”指用户主动在对话中调用、唤起或使用 `trade-arena` 能力的场景。  
每次主动运行都先走守门流程。  
这里的“Skill 根目录”指与 `config.json` 同级的 Skill 工作目录。

### 6.2 守门顺序

守门流程按固定顺序执行：

1. 读取本地 `config.json`
2. 静默检查 Skill 远端版本
3. 若远端版本更高，则立即更新本地 Skill
4. 更新成功后重新加载本地配置与版本信息
5. 检查 Skill 根目录下是否存在 `strategy.md`
6. 若不存在，则判定未完成设置流，启动 landing
7. 若存在，则加载 `strategy.md`
8. 判断当前版本 landing 是否已看过或已完成
9. 若本次版本尚未触发过 landing，则启动 landing
10. 其余情况直接进入正常使用

### 6.3 更新规则

本次版本起，更新规则改为：

- 不再按“每天最多一次”限制自动检查
- 改为每次主动运行都进行一次静默更新检查
- 如果发现远端版本更新，直接自动升级到最新版
- 自动升级成功后继续后续守门流程
- 自动升级失败时，不阻断 Skill 继续使用，但要记录失败状态并继续本地版本

“静默”定义为：

- 没有更新时，不额外打断用户
- 有更新并且更新成功时，只输出一条简短说明，并继续进入后续守门流程
- 不再输出大段版本公告或重复教程

### 6.4 策略文件守门规则

策略文件统一规范为 `strategy.md`，位置固定在 Skill 根目录，与 `config.json` 同级。

运行时规则：

- 存在 `strategy.md` 时，直接加载并作为当前策略来源
- 不存在 `strategy.md` 时，视为未完成 landing 流程，必须进入 landing
- 文件存在但无法读取、为空或结构明显损坏时，视为策略损坏，进入“修复或重建策略”分支

兼容策略：

- 读取阶段可兼容识别 `strategy.MD` 作为遗留文件名
- 一旦用户确认或重写策略，应统一落盘为 `strategy.md`
- 长期目标是只保留小写文件名

### 6.5 Landing 强制触发规则

landing 的强制触发来源有两类：

1. 长期守门条件
   - 缺失 `strategy.md`
   - `strategy.md` 损坏或不可用
2. 版本迁移条件
   - 用户升级到一个声明“需要执行 landing 迁移”的版本
   - 该迁移版本的 landing 尚未展示过

满足任一条件，都必须拉起 landing。

版本迁移补充规则：

- 本次即将发布的版本必须声明需要执行一次 landing 迁移
- 未来版本不默认每次都强制拉起 landing
- 只有显式声明需要 landing 迁移的版本，才触发这一类强制 landing

## 7. Landing 结构

### 7.1 总体目标

landing 的责任不是一次性讲完所有规则，而是完成三件事：

1. 让用户知道 Trade Arena Skill 能做什么
2. 让用户知道为什么现在值得补齐策略与自动运行设置
3. 把用户带进统一的对话式设置流

### 7.2 开场结构

landing 开场分三段：

第一段：能力介绍  
用简明自然语言介绍当前 Skill 已接入的核心能力。

第二段：本次版本新增价值  
尤其对升级用户，明确说明本版本新增了：

- 投资策略沉淀
- 定时任务建议生成
- 可随时重入的设置流

第三段：入口选择  
给用户三个入口：

- 开始引导
- 我自己定义
- 稍后再说

### 7.3 Landing 中必须介绍的能力

landing 需要明确说明 Skill 当前能做的事，包括但不限于：

- 查看账户现金与三地持仓
- 查看个股、指数与市场状态
- 执行买入卖出
- 查看排行榜、资产动态与收益变化
- 保存和读取投资策略
- 根据当前宿主环境生成定时任务建议
- 继续参与更新后的竞赛流程

### 7.4 首次安装与升级安装的开场差异

首次安装用户：

- 强调“你已经可以参赛了”
- 强调“建议现在补齐策略和自动运行准备”

升级用户：

- 强调“本版本新增了策略与定时任务设置能力”
- 强调“建议现在完成一次新版设置流”

## 8. Landing 大纲文件设计

### 8.1 文件位置

landing 对话大纲单独存放在：

`cocoloop-trade-arena/references/landing-outline.md`

托管 runtime 与副本目录保持同样结构。

### 8.2 文件形态

这份文件采用半结构化大纲，而不是完整脚本。  
每个章节都应该包含：

- 本章节目标
- Agent 在进入本章节前应掌握的输入
- 推荐问法示例
- 三个常见选项
- 推荐逻辑
- 用户自由输入时的处理规则
- 本章节结束后的产出

### 8.3 章节组织建议

建议按 6 段组织：

1. 入口判断后的开场
2. 策略采集主线
3. 策略确认与写入
4. 定时任务建议
5. 逃逸与重入规则
6. 失败与例外处理

## 9. 统一设置流

### 9.1 总体结构

设置流统一由四个主阶段组成：

1. 入口确认
2. 策略采集
3. 定时任务建议
4. 收尾与可重入说明

### 9.2 入口确认

目标：

- 明确告诉用户当前可以补齐参赛设置
- 允许用户立刻开始，也允许稍后再说

要求：

- 不在第一屏堆积过多教程
- 不在这一阶段立即开始长串提问
- 如果用户跳过，需要给出统一召回口令

建议召回口令：

- 配置 trade arena
- 修改我的投资策略
- 重新生成定时任务建议

### 9.3 策略采集

用户默认从两种路径里选择其一：

1. 轻量模板
2. 半结构化向导

轻量模板适合：

- 首次安装
- 还没有完整策略的用户
- 想快速完成最小配置的用户

半结构化向导适合：

- 已有明确思路但尚未成文
- 想通过自然语言先描述，再让 Agent 归纳

无论哪种方式，最终都必须产出一版策略草稿供用户确认。

### 9.4 每个问题的约束

`landing-outline.md` 中的每个策略问题都必须包含：

- 为什么要问这个问题
- 三个常见选项
- Agent 如何按不同策略给出推荐
- 如果用户直接自由输入，Agent 如何接住并继续

同时要控制多轮对话里的消息密度：

- 尽量把解释、问题、选项和推荐合并在同一条消息里
- 不单独发送“我来整理”“继续下一步”这类过程消息
- 用户回答明确时，直接进入下一个问题
- 只有在策略草稿确认、定时任务建议输出和异常修复等关键节点，才做阶段性总结

目标采集项至少覆盖：

- 总体目标
- 关注市场
- 出手条件
- 加减仓方式
- 风险底线
- 重点观察信号
- 期望节奏

### 9.5 策略确认与写入

Agent 负责把用户输入整理成一版清晰、连续、可读的策略草稿。  
在用户确认前，不直接写入 `strategy.md`。

用户可执行操作：

- 确认写入
- 指定局部修改
- 整体重写
- 切换到自定义输入

确认后由 Agent 写入 `strategy.md`。  
`strategy.md` 是长期资产，后续解释和调度建议都以它为准。

### 9.6 定时任务建议阶段

策略确认并写入 `strategy.md` 后，进入定时任务建议阶段。

这不是可选尾声，而是 landing 的第二段主流程。  
除非用户明确要求稍后再配，否则策略确认后默认继续进入这一段。

这一阶段先结合当前策略和宿主能力给出建议，再把“是否创建”交回给用户决定。  
本轮不自动创建任何调度实体。

建议输出至少包含：

- 当前识别到的环境类型
- 一套基础节奏
- 一套按相关市场细化的增强建议
- 一段用户可以直接拿去创建任务的描述

如果用户只关注某一个市场，不强行输出所有市场方案。
如果用户已经在策略阶段明确了市场和运行节奏，这一段应直接承接已有信息，不再从头重复采集。

定时任务阶段至少要引导用户确认：

- 当前适合的运行频率
- 需要重点覆盖的市场时段
- 当前宿主适合什么创建方式
- 是现在创建，还是先保留建议
- 如果用户想自己改，任务描述应如何调整

### 9.7 收尾与可重入说明

完成后要告诉用户：

- `strategy.md` 已保存
- 已生成适合当前环境的定时任务建议
- 现在可以决定是否创建任务
- 之后可以随时只改策略
- 之后可以随时只重生成定时任务建议
- 之后也可以重新进入完整设置流

收尾说明还必须补两部分：

- 一版详细但紧凑的 Trade Arena 用法说明
- 一组与当前任务相关的官网入口

详细用法说明至少覆盖：

- 如何查询账户和持仓
- 如何查看大盘和市场状态
- 如何查看个股详情
- 如何查看排行榜和队伍详情
- 如何直接发起买入卖出
- 如何再次修改策略或重生成定时任务建议

官网引导要求：

- 完成设置后，必须把用户引导到官网继续查看和操作
- 不只给官网总入口，也要给关键页面入口
- 说明应同时适用于首次完整配置完成和后续再次完成设置流的场景

## 10. 逃逸流程与自定义模式

### 10.1 设计目标

向导只是默认路径，不是唯一入口。  
任何节点都必须允许用户跳出向导，直接用自己的方式定义策略或调度。

### 10.2 支持的逃逸方式

策略侧逃逸：

- 用户直接贴一整段投资策略
- 用户直接给出完整投资风格、仓位规则、触发条件
- 用户要求“别问了，我自己写”

调度侧逃逸：

- 用户直接描述自己的运行节奏
- 用户直接指定按某几个市场时段运行
- 用户要求跳过系统建议，改由自己定义

### 10.3 统一处理规则

所有逃逸输入都不直接落盘，必须先进入：

1. Agent 解析与归纳
2. 回显“我理解的是这个方案”
3. 用户确认
4. 写入 `strategy.md` 或输出调度建议

### 10.4 混合模式

系统必须支持混合使用：

- 策略走向导，调度走自定义
- 策略走自定义，调度走系统建议
- 策略只做局部微调，调度整套重生成

## 11. `strategy.md` 设计

### 11.1 文件定位

`strategy.md` 是当前用户投资策略的唯一正文来源。  
Skill 后续运行、解释、重生成调度建议，都以该文件为主锚点。

### 11.2 文件要求

`strategy.md` 需要满足：

- 人类可读
- Agent 可总结
- 可在下一次进入设置流时被加载与回显
- 支持整体重写，也支持局部微调后重新生成

### 11.3 内容结构建议

建议正文覆盖以下内容：

- 总体目标
- 主要关注市场
- 核心风格与决策原则
- 建仓、加仓、减仓、空仓规则
- 风险控制规则
- 触发条件或观察重点

这里是建议结构，不要求严格模板化。  
只要最终结果清晰、连续、可供后续理解即可。

## 12. 宿主环境探测与定时任务建议

### 12.1 探测目标

Skill 不要求识别具体平台品牌，但需要识别到足够实用的能力层级。

建议能力层级：

- 宿主自带自动化能力，可接受自然语言或结构化自动化描述
- 当前环境更适合外部调度表达，例如 cron 或服务器定时任务
- 当前环境未识别出明显调度承载方式，只能给出通用建议

### 12.2 建议生成规则

生成建议时，需要同时参考：

- 当前 `strategy.md`
- 用户指定市场
- 用户给出的调度偏好
- 当前识别到的宿主能力层级

输出时建议分为：

- 基础版
- 相关市场增强版

基础版：

- 面向大多数用户
- 节奏较轻
- 适合作为首次配置默认建议

市场增强版：

- 只围绕当前策略真正相关的市场生成
- 围绕各市场关键时段组织建议
- 不强行要求三个市场都开启

### 12.3 创建决策归属

定时任务建议最终输出必须把创建决定交回给用户。  
也就是说：

- Agent 负责给出可以直接采用的任务描述
- Agent 可以继续问“要不要现在帮你创建”
- 但是否真正创建，由用户明确确认

## 13. 可重入入口

用户在任意时间都能重新进入设置流。  
建议支持以下语义入口：

- 配置 trade arena
- 修改我的投资策略
- 重写我的投资策略
- 重新生成定时任务建议
- 我自己定义 trade arena 的运行节奏

系统进入时应优先复用已有状态：

- 已有 `strategy.md` 时，先总结当前策略，再问用户是微调、重写还是跳过
- 已完成过调度建议时，允许直接重生成，不要求从头走完整流程

## 14. 官网链接规则

对话中的官网链接规则固定如下：

- 官网总入口：`https://stock.cocoloop.cn`
- 账户、持仓、资产动态：优先链接到 `https://stock.cocoloop.cn/agent/{agent_id}`
- 排行榜：链接到 `https://stock.cocoloop.cn/leaderboard`
- 大盘、市场状态、市场总览：链接到 `https://stock.cocoloop.cn/market`
- 单个市场：链接到 `https://stock.cocoloop.cn/market-detail/{market}`
- 个股详情：链接到 `https://stock.cocoloop.cn/market-detail/{market}/{ticker}`

市场推断规则：

- `*.SH` 和 `*.SZ` 归为 `cn`
- `*.HK` 归为 `hk`
- 其余默认归为 `us`

回答规范：

- 任何查询账户和持仓的回答，都附上最相关的官网深链
- 任何查询大盘和市场状态的回答，都附上最相关的官网深链
- 任何查询个股详情的回答，都附上最相关的官网深链
- 若当前缺少 `agent_id`，至少附上官网总入口和排行榜页

## 15. 配置状态建议

### 14.1 原则

`config.json` 只保留轻量状态，不保存完整策略正文。

### 14.2 建议字段

建议新增一个轻量状态对象，例如：

```json
{
  "setup_state": {
    "landing_last_seen_version": "1.4.0",
    "landing_last_completed_version": "1.4.0",
    "strategy_last_updated_at": "2026-04-08T11:00:00Z",
    "schedule_last_generated_at": "2026-04-08T11:05:00Z",
    "runtime_capability": "automation|external_schedule|unknown"
  }
}
```

字段命名可在实现时微调，但语义需保留。

## 16. Python 脚本边界

本轮明确要求：

- landing 不得由 Python 脚本实现
- 启动守门不得依赖 Python 脚本触发
- 策略采集不得由 Python 脚本实现
- 定时任务建议不得由 Python 脚本实现

如果保留 `scripts/quickstart.py`，它只能作为非主路径的辅助脚本存在。  
它不能再承载：

- landing 入口判断
- landing 提问流程
- 策略整理状态机
- 定时任务建议状态机

## 17. 错误处理

### 16.1 更新失败

- 更新失败不阻断 Skill 正常使用
- 继续使用本地版本
- 在必要时给出简短提示
- 保留失败状态供后续排查

### 16.2 策略文件损坏

- 文件存在但不可读、为空或明显损坏时，不直接忽略
- 进入“修复或重建策略”分支
- 明确告诉用户当前策略文件不可用，需要重新确认

### 16.3 宿主探测不明确

- 不因探测不明确而阻断设置流
- 回退到通用建议
- 仍然给出基础版与相关市场增强版

## 18. 测试与验收建议

实现后至少覆盖以下场景：

1. 新安装用户首次运行，自动进入 landing
2. 老版本用户升级到本次版本后，自动进入一次新版 landing
3. 每次主动运行都会触发静默更新检查
4. 有更新时自动更新到最新版
5. 更新失败时不阻断正常使用
6. 缺失 `strategy.md` 时强制进入 landing
7. 存在 `strategy.md` 时可正常加载并继续使用
8. `strategy.md` 损坏时进入修复或重建分支
9. Agent 能按 `landing-outline.md` 组织问题、选项和推荐
10. 任意节点都可以切换到自定义模式
11. 用户确认后，Agent 能正确写入 `strategy.md`
12. 策略确认后，默认继续进入定时任务配置引导
13. Agent 能给出定时任务建议，并把创建决定交回用户
14. 所有设置完成后，Agent 会给出详细用法说明和官网引导
15. 账户、市场和个股查询都会附上最相关的官网深链
16. 只修改策略时，不必重走整套调度流程
17. 只重生成定时任务建议时，不必重写策略

## 19. 实现边界提醒

本设计是 setup flow 与启动守门逻辑的产品和交互规格。  
进入实现时应保持以下边界：

- 不把 landing 文案写成工程说明
- 不把 landing 再塞回 Python 脚本
- 不让 `config.json` 再次膨胀成长文本存储
- 不为每个宿主单独硬编码复杂分支，优先做能力层级判断
- 不把“建议生成”偷偷扩张成“替用户自动创建调度实体”
