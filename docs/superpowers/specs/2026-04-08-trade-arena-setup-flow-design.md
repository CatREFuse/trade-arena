# Trade Arena Skill 安装落地与参赛设置流设计

最后更新：2026-04-08（Asia/Shanghai）
状态：已确认方案，待实现
适用范围：`cocoloop-trade-arena/` Skill 包、托管 runtime、副本 `skill-runtime/cocoloop-trade-arena/`、相关说明文档

## 1. 目标

本设计解决四件事：

1. 把 `trade-arena` 从“装完就能调用工具”的 Skill，升级成“装完就能进入参赛设置”的 Skill。
2. 为用户建立一套可反复进入的统一设置流，帮助其沉淀投资策略，并生成适合当前宿主环境的定时任务建议。
3. 让所有老版本安装者在升级到本次版本后，至少被拉起一次新版 landing，知道新增能力并完成必要配置。
4. 把每次主动运行 Skill 的启动逻辑收口成统一守门流程，自动静默检查更新，并用 `strategy.md` 是否存在来判断是否完成过设置流。

最终结果应满足：

- 首次安装后自动进入 landing
- 老版本用户升级到本次版本后自动进入一次新版 landing
- 每次主动运行 Skill 都会先静默检查更新，若有更新则直接更新到最新版
- 每次主动运行 Skill 都会检查当前工作区是否存在 `strategy.md`
- `strategy.md` 不存在时，视为未完成设置流，必须进入 landing
- `strategy.md` 存在时，Skill 会加载当前策略并据此继续工作
- 投资策略既支持向导，也支持用户任意节点跳出向导改用自定义输入
- 定时任务建议既支持系统推荐，也支持用户任意节点直接给出自己的调度要求
- 定时任务建议不直接替用户创建，只负责探测当前宿主能力并输出可直接采用的建议表达

## 2. 非目标

本轮不做下面几项：

- 不替用户直接创建 automation、cron、systemd timer 或其他宿主调度实体
- 不把完整投资策略正文写进 `config.json`
- 不在网站首页复制一套完整设置流；本轮主入口是 Skill 安装后的 landing
- 不引入复杂的多文件策略仓库管理；本轮只维护一份主策略文件
- 不追求对所有 Agent 宿主的绝对精准识别；本轮只要求识别到足够实用的能力层级

## 3. 现状问题

### 3.1 Landing 只做基础说明，无法把用户带到可自动运行状态

当前 Skill 安装完成或更新完成后会输出一段纯文本说明，内容聚焦：

- 安装 Skill
- 查询账户与持仓
- 查看行情、排行榜、资产动态
- 执行交易

这能让用户知道“能做什么”，但还缺少两项对持续参赛最关键的能力：

- 如何把投资策略沉淀成可复用的文件
- 如何在当前宿主环境里形成持续运行的定时任务方案

### 3.2 旧版用户升级后不会自动感知新增设置能力

当前自更新逻辑只在每日最多一次检查新版本，发现更新时替换文件并重新输出一次说明。  
这不足以保证老版本用户真正知道“新版引入了策略与定时任务设置流”，也不足以保证他们至少进入一次新版 landing。

### 3.3 策略没有统一文件锚点

当前 Skill 配置以 `config.json` 为主，适合保存 token、账号 ID、版本号等结构化配置。  
但投资策略本身是长文本、需要反复修改、需要被总结和回显的内容，不适合直接塞进 `config.json`。

### 3.4 每次运行前的准备逻辑分散

当前运行时主要做的是：

- 读取 `config.json`
- 检查是否需要每日更新
- 按工具调用继续执行

缺少一个统一的“启动守门流程”来决定：

- 是否要先自动更新
- 是否已经有策略文件
- 是否需要强制拉起新版 landing
- 是否可以直接进入正常使用

## 4. 设计原则

1. 单一路径。首次安装、旧版升级、日后修改都走同一套设置流。
2. 先解释，再采集。landing 先说明 Trade Arena 能做什么，再引导策略和调度配置。
3. 默认引导，随时逃逸。向导是默认路径，但任何节点都允许用户切到自定义输入。
4. 以文件为锚。完整策略正文统一写入 `strategy.md`。
5. 配置最小化。`config.json` 只保存流程状态和必要元信息，不保存整篇策略正文。
6. 启动守门。每次主动运行 Skill 先完成更新检查与策略文件检查，再决定是否进入 landing。
7. 自动追版本。只要远端有新版本，主动运行时就直接升级到最新版。
8. 不替用户越权。定时任务建议负责探测与翻译，不直接代替宿主创建调度实体。
9. 可重入。用户以后任意时间都能再次进入同一流程，修改策略或重生成调度建议。
10. 自然语言优先。用户主入口是 Skill 对话，不要求用户直接运行本地 Python 脚本。

## 5. 总体方案

整体收成三层：

### 5.1 启动守门层

每次主动运行 Skill 时，先进入统一守门流程：

1. 静默检查远端最新版本
2. 如果有更新，直接更新到最新版
3. 检查并加载 Skill 根目录下的 `strategy.md`
4. 判断是否需要强制拉起 landing
5. 满足条件后再进入正常工具能力

### 5.2 参赛设置流层

设置流是一个可重复进入的对话式 flow，由以下能力组成：

- landing 能力介绍
- 策略采集
- 策略确认与写入 `strategy.md`
- 宿主环境探测
- 定时任务建议生成
- 任意节点跳到自定义输入

### 5.3 轻量状态层

`config.json` 内只记录最少状态，用于支撑：

- 当前已见过哪个版本的 landing
- 当前已完成哪个版本的 landing
- 最近一次策略更新时间
- 最近一次定时任务建议更新时间
- 最近一次策略采集模式
- 最近一次探测到的宿主能力层级

## 6. 启动守门流程

### 6.1 触发范围

“主动运行 Skill”指用户主动在对话中调用、唤起或使用 `trade-arena` 能力的场景。  
每次主动运行都先走守门流程。  
这里的“Skill 根目录”指与 `config.json` 同级的 Skill 工作目录。

### 6.2 守门顺序

守门流程按固定顺序执行：

1. 读取本地 `config.json`
2. 静默检查 Skill 远端版本
3. 若远端版本更高，则立即更新本地 Skill
4. 更新成功后重新加载本地配置与版本信息
5. 检查 Skill 根目录下是否存在 `strategy.md`
6. 若不存在，则判定未完成设置流，启动 landing
7. 若存在，则加载 `strategy.md`
8. 判断当前版本 landing 是否已看过或已完成
9. 若本次版本尚未触发过 landing，则启动 landing
10. 其余情况直接进入正常使用

### 6.3 更新规则

本次版本起，更新规则改为：

- 不再按“每天最多一次”限制自动检查
- 改为每次主动运行都进行一次静默更新检查
- 如果发现远端版本更新，直接自动升级到最新版
- 自动升级成功后继续后续守门流程
- 自动升级失败时，不阻断 Skill 继续使用，但要记录失败状态并继续本地版本

“静默”定义为：

- 没有更新时，不额外打断用户
- 有更新并且更新成功时，只输出一条简短说明，并继续进入后续守门流程
- 不再输出大段版本公告或重复教程

### 6.4 策略文件守门规则

策略文件统一规范为 `strategy.md`，位置固定在 Skill 根目录，与 `config.json` 同级。

运行时规则：

- 存在 `strategy.md` 时，直接加载并作为当前策略来源
- 不存在 `strategy.md` 时，视为未完成 landing 流程，必须进入 landing
- 文件存在但无法读取、为空或结构明显损坏时，视为策略损坏，进入“修复或重建策略”分支

兼容策略：

- 读取阶段可兼容识别 `strategy.MD` 作为遗留文件名
- 一旦用户确认或重写策略，应统一落盘为 `strategy.md`
- 长期目标是只保留小写文件名
- 更新流程不得覆盖现有 `strategy.md`

### 6.5 Landing 强制触发规则

landing 的强制触发来源有两类：

1. 长期守门条件
   - 缺失 `strategy.md`
   - `strategy.md` 损坏或不可用
2. 版本迁移条件
   - 用户升级到一个声明“需要执行 landing 迁移”的版本
   - 该迁移版本的 landing 尚未展示过

满足任一条件，都必须拉起 landing。

版本迁移补充规则：

- 本次即将发布的版本必须声明需要执行一次 landing 迁移
- 未来版本不默认每次都强制拉起 landing
- 只有显式声明需要 landing 迁移的版本，才触发这一类强制 landing

## 7. Landing 结构

### 7.1 总体目标

landing 的责任不是一次性讲完所有规则，而是完成三件事：

1. 让用户知道 Trade Arena Skill 能做什么
2. 让用户知道为什么现在值得补齐策略与自动运行设置
3. 把用户带进统一的设置流

### 7.2 开场结构

landing 开场分三段：

第一段：能力介绍  
用简明自然语言介绍当前 Skill 已接入的核心能力。

第二段：本次版本新增价值  
尤其对升级用户，明确说明本版本新增了：

- 投资策略沉淀
- 定时任务建议生成
- 可随时重入的设置流

第三段：入口选择  
给用户三个入口：

- 开始引导
- 我自己定义
- 稍后再说

### 7.3 Landing 中必须介绍的能力

landing 需要明确说明 Skill 当前能做的事，包括但不限于：

- 查看账户现金与三地持仓
- 查看个股、指数与市场状态
- 执行买入卖出
- 查看排行榜、资产动态与收益变化
- 保存和读取投资策略
- 根据当前宿主环境生成定时任务建议
- 继续参与更新后的竞赛流程

### 7.4 首次安装与升级安装的开场差异

首次安装用户：

- 强调“你已经可以参赛了”
- 强调“建议现在补齐策略和自动运行准备”

升级用户：

- 强调“本版本新增了策略与定时任务设置能力”
- 强调“建议现在完成一次新版设置流”

## 8. 统一设置流

### 8.1 总体结构

设置流统一由四个主状态组成：

1. 入口确认
2. 策略采集
3. 宿主环境探测与定时任务建议
4. 收尾与可重入说明

### 8.2 入口确认

目标：

- 明确告诉用户当前可以补齐参赛设置
- 允许用户立刻开始，也允许稍后再说

要求：

- 不在第一屏堆积过多教程
- 不在这一阶段立即开始长串提问
- 如果用户跳过，需要给出统一召回口令

建议召回口令：

- 配置 trade arena
- 修改我的投资策略
- 重新生成定时任务建议

### 8.3 策略采集

用户先选择两种策略采集方式之一：

1. 轻量模板
2. 半结构化向导

轻量模板适合：

- 首次安装
- 还没有完整策略的用户
- 想快速完成最小配置的用户

半结构化向导适合：

- 已有明确思路但尚未成文
- 想通过自然语言先描述，再让 Skill 归纳

无论哪种方式，最终都必须产出一版策略草稿供用户确认。

### 8.4 策略草稿确认

Skill 负责把用户输入整理成一版清晰、连续、可读的策略草稿。  
在用户确认前，不直接写入 `strategy.md`。

用户可执行操作：

- 确认写入
- 指定局部修改
- 整体重写
- 切换到自定义输入

### 8.5 定时任务建议阶段

策略确认并写入 `strategy.md` 后，进入定时任务建议阶段。  
这一阶段先探测宿主环境，再生成建议。

建议输出永远包含两档：

1. 基础版节奏
2. 市场增强版节奏

基础版节奏面向大多数用户，负担低。  
市场增强版按 A 股、港股、美股拆开，并结合当前 `strategy.md` 的风格做微调。

### 8.6 收尾与可重入说明

完成后要告诉用户：

- `strategy.md` 已保存
- 已生成适合当前环境的定时任务建议
- 之后可以随时只改策略
- 之后可以随时只重生成定时任务建议
- 之后也可以重新进入完整设置流

## 9. 逃逸流程与自定义模式

### 9.1 设计目标

向导只是默认路径，不是唯一入口。  
任何节点都必须允许用户跳出向导，直接用自己的方式定义策略或调度。

### 9.2 支持的逃逸方式

策略侧逃逸：

- 用户直接贴一整段投资策略
- 用户直接给出完整投资风格、仓位规则、触发条件
- 用户要求“别问我了，我自己写”

调度侧逃逸：

- 用户直接描述自己的运行节奏
- 用户直接指定按某几个市场时段运行
- 用户要求跳过系统建议，改由自己定义

### 9.3 统一处理规则

所有逃逸输入都不直接落盘，必须先进入：

1. Skill 解析与归纳
2. 回显“我理解的是这个方案”
3. 用户确认
4. 写入 `strategy.md` 或生成调度建议

### 9.4 混合模式

系统必须支持混合使用：

- 策略走向导，调度走自定义
- 策略走自定义，调度走系统建议
- 策略只做局部微调，调度整套重生成

## 10. `strategy.md` 设计

### 10.1 文件定位

`strategy.md` 是当前用户投资策略的唯一正文来源。  
Skill 后续运行、解释、重生成调度建议，都以该文件为主锚点。

### 10.2 文件要求

`strategy.md` 需要满足：

- 人类可读
- Agent 可总结
- 可在下一次进入设置流时被加载与回显
- 支持整体重写，也支持局部微调后重新生成

### 10.3 内容结构建议

建议正文覆盖以下内容：

- 总体目标
- 主要关注市场
- 核心风格与决策原则
- 建仓、加仓、减仓、空仓规则
- 风险控制规则
- 触发条件或观察重点
- 调度偏好说明

这里是建议结构，不要求严格模板化。  
只要最终结果清晰、连续、可供后续理解即可。

## 11. 宿主环境探测与定时任务建议

### 11.1 探测目标

Skill 不要求识别具体平台品牌，但需要识别到足够实用的能力层级。

建议能力层级：

- 宿主自带自动化能力，可接受自然语言或结构化自动化描述
- 当前环境更适合外部调度表达，例如 cron 或服务器定时任务
- 当前环境未识别出明显调度承载方式，只能给出通用建议

### 11.2 建议生成规则

生成建议时，需要同时参考：

- 当前 `strategy.md`
- 用户指定市场
- 用户给出的调度偏好
- 当前识别到的宿主能力层级

输出时必须分为：

- 基础版
- 市场增强版

基础版：

- 面向大多数用户
- 节奏较轻
- 适合作为首次配置默认建议

市场增强版：

- 分别给出 A 股、港股、美股的增强建议
- 围绕各市场关键时段组织建议
- 不强行要求三个市场都开启

### 11.3 输出格式要求

定时任务建议最终输出必须包含三块：

1. 当前识别到的环境类型
2. 推荐运行节奏
3. 当前用户可以直接采用的设置语句或配置草案

输出目标是“拿去就能用”，而不是只给抽象说明。

### 11.4 不直接创建调度实体

本轮只负责：

- 探测
- 推荐
- 翻译成宿主易用表达

本轮不负责：

- 直接新建 automation
- 直接写入 cron
- 直接创建系统定时器

## 12. 可重入入口

用户在任意时间都能重新进入设置流。  
建议支持以下语义入口：

- 配置 trade arena
- 修改我的投资策略
- 重写我的投资策略
- 重新生成定时任务建议
- 我自己定义 trade arena 的运行节奏

系统进入时应优先复用已有状态：

- 已有 `strategy.md` 时，先总结当前策略，再问用户是微调、重写还是跳过
- 已完成过调度建议时，允许直接重生成，不要求从头走完整流程

## 13. 配置状态建议

### 13.1 原则

`config.json` 只保留轻量状态，不保存完整策略正文。

### 13.2 建议字段

建议新增一个轻量状态对象，例如：

```json
{
  "setup_state": {
    "landing_last_seen_version": "1.3.0",
    "landing_last_completed_version": "1.3.0",
    "strategy_last_updated_at": "2026-04-08T11:00:00Z",
    "strategy_capture_mode": "guided|template|custom",
    "schedule_last_generated_at": "2026-04-08T11:05:00Z",
    "runtime_capability": "automation|external_schedule|unknown"
  }
}
```

字段命名可在实现时微调，但语义需保留。

## 14. 错误处理

### 14.1 更新失败

- 更新失败不阻断 Skill 正常使用
- 继续使用本地版本
- 在必要时给出简短提示
- 保留失败状态供后续排查

### 14.2 策略文件损坏

- 文件存在但不可读、为空或明显损坏时，不直接忽略
- 进入“修复或重建策略”分支
- 明确告诉用户当前策略文件不可用，需要重新确认

### 14.3 宿主探测不明确

- 不因探测不明确而阻断设置流
- 回退到通用建议
- 仍然给出基础版与市场增强版

## 15. 测试与验收建议

实现后至少覆盖以下场景：

1. 新安装用户首次运行，自动进入 landing
2. 老版本用户升级到本次版本后，自动进入一次新版 landing
3. 每次主动运行都会触发静默更新检查
4. 有更新时自动更新到最新版
5. 更新失败时不阻断正常使用
6. 缺失 `strategy.md` 时强制进入 landing
7. 存在 `strategy.md` 时可正常加载并继续使用
8. `strategy.md` 损坏时进入修复或重建分支
9. 向导模式可以写出策略草稿并落盘
10. 任意节点都可以切换到自定义模式
11. 只修改策略时，不必重走整套调度流程
12. 只重生成定时任务建议时，不必重写策略
13. 宿主能力明确时能输出对应建议表达
14. 宿主能力不明确时能退回通用建议

## 16. 实现边界提醒

本设计是 setup flow 与启动守门逻辑的产品和交互规格。  
进入实现时应保持以下边界：

- 不把 landing 文案写成工程说明
- 不把向导问题写得过多过深，避免首次体验过重
- 不为每个宿主单独硬编码复杂分支，优先做能力层级判断
- 不让 `config.json` 再次膨胀成长文本存储
- 不把“建议生成”偷偷扩张成“替用户自动创建调度实体”
